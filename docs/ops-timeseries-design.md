> 当前实现已改用 TDengine：订单样本先与业务数据在 PostgreSQL 同一事务写入 `ipe_ops.order_telemetry_outbox`，后台按顺序写入 TDengine，成功后删除发件箱记录；失败保留并重试。查询遇到待同步记录会返回错误，避免把未同步的数据当成完整结果。TDengine 数据库 `ipe_telemetry` 使用微秒精度，保留 3650 天；指标采用 DOUBLE，存在浮点精度限制。时间戳相同的部分字段按 TDengine 的部分列更新合并。发件箱需要监控积压，单条持续写入失败会阻塞后续同步。接收时间不能保证设备重传去重。服务端只安装中间件，不部署项目代码。

# 充电过程时序与订单回放设计

> 已接入基础时序采集和订单回放，数据库集成验证和长订单分页等增强待完成。禁止将应用代码上传或部署到个人服务器；服务器凭据不写入源码、文档、配置或 Git。本文延续独立 schema、无业务外键的数据库要求。

## 目标与选型

使用 TimescaleDB（PostgreSQL 时序扩展）保存订单充电期间的过程数据，并按订单和枪口查询曲线。TimescaleDB 的 hypertable 按时间切分，仍以 PostgreSQL 接口访问；可沿用 Java/JDBC 工具链。时序数据与业务表位于同一个 TimescaleDB 数据库及 `ipe_ops` schema，使用同一个数据源和本地事务；禁止业务表落到 `public`。安装与应用部署是独立动作；本期不上传或部署项目代码。参考 [TimescaleDB hypertable 文档](https://www.tigerdata.com/docs/reference/timescaledb/hypertables)。

## 数据与关联

一条样本包含 `sample_time timestamptz`、`received_at timestamptz`、`order_no`、`device_id`、`connector_no`、`protocol_code`，以及电压 V、电流 A、功率 kW、枪线温度 ℃、电池温度 ℃、SOC % 的可空 numeric 字段。未上报的值保持 NULL，禁止用上一条或零填充。单个指标可以独立有值，不假定设备每次同时上报全部指标。数据类型和单位统一转换，保留来源与时间质量：设备时间/平台接收时间；不要把接收时间伪装为设备采样时间。功率只在设备明确上报或计算条件足够时产生；推导值必须标注来源，不可无条件用电压乘电流代替三相功率。

以订单号、设备、枪号和采样时间查询；新数据写入时即关联订单号，避免同设备/枪号相邻或重叠订单仅靠时间窗口误归属。协议事务号优先关联并校验设备、枪号；无事务号时仅在该枪恰有一个有效订单且事件时间属于订单窗口时关联，否则不计入回放并保留异常记录。已结束订单的迟到数据按可信设备事件时间和协议事务号匹配；缺少可靠时间或唯一身份时不能猜测归属。

Hypertable 的唯一索引必须包含时间分区列。设计稳定、协议可重放的来源事件键，按 `(sample_time, protocol_code, device_id, connector_no, source_key)` 去重；无法从协议获得稳定事件标识时应明确采用可复现的消息标识或标记去重能力不足，不用收到时间伪装幂等键。建立 `(order_no, sample_time)` 查询索引；不使用数据库外键。当前采样与订单写入共用同一数据库连接和事务；后续若拆分数据库，需要引入事务 outbox，不能假设跨库本地事务原子。保留策略明确配置，删除时序历史前应明确回放受影响范围。

## 需要修改的现有链路

- 云快充实时数据经过 `InternalTelemetryController.gunState`；它携带枪号、事务号、电压、电流、SOC、枪线及电池温度，但当前属性映射对 0 ℃ 会丢弃，需按协议的无效值定义判断，不要简单按正负过滤。报文若无采样时间，标记平台接收时间。
- OCPP `MeterValues` 当前把多个 `meterValue` 合并成一个样本，只读取电压、电流、SOC 和累计电量，忽略采样时间、功率和温度。应逐个 `meterValue` 保留 timestamp 和 sampledValue，转换单位，处理 measurand、phase、location；未知单位或不支持的相位不随意合并。分别修改 protocol 与 ops 两侧 DTO，并保持模拟器可验证。必须校验 transactionId 所属设备和 connector，不能跨桩串单。
- 产品/设备实时属性仍服务实时界面；历史时序与订单过程样本职责区分，不能双写不同语义后悄悄合并。旧普通表 `device_property_ts` 的替代与保留策略应与数据库重建一起实施，不向 `public` 写入。

## 回放 API 与前端

`GET /api/ops/orders/{orderNo}/telemetry` 先验证订单存在及访问权限，再按订单号查询时序库。响应包含订单起止、采样时间来源、每个指标的单位和时间点、缺失/延迟状态；订单未结束时结束边界为当前时间。大订单按时间范围、游标或分桶上限查询；下采样保留首尾和极值，不把缺失段连成真实连续数据。时序库不可用返回明确错误，不能返回空数组假装没有数据。

订单详情新增「充电过程回放」：以统一时间轴展示电压、电流、功率、温度、SOC 分图，支持范围选择、拖动时间轴、播放/暂停、速度选择与悬浮查看；不同单位不得共用误导性的 Y 轴。数据显示真实时间及缺口，并区分设备时间与接收时间。订单仍在充电时支持刷新，历史订单固定边界。历史时序数据不存在时显示「暂无过程数据」。

## 验证

覆盖两种协议、同桩多枪及相邻订单、缺失值、零温度、单位和相位、时间偏移/乱序/补传、重复投递、时序库暂不可用后恢复、长订单分页和下采样、schema 隔离、无外键、权限和浏览器交互。先使用独立测试库验证，不运行会清空现有数据库的脚本；代码未完成前不得以曲线占位冒充真实回放。

## 当前实现限制

当前用订单号与采样时间去重；没有设备时间的云快充数据按接收时间写入，不能保证重传去重。暂不处理结束后的迟到样本，超过 10000 点仅返回最早数据并标明截断，回放以样本点速度播放；时序迁移需要预先安装并启用 TimescaleDB 扩展。本地尚未完成真实 TimescaleDB 的迁移及端到端验证。
