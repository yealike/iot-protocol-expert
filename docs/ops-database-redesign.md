# 运营平台数据库重建设计

> 设计稿，尚未执行或接入。个人 demo 允许丢弃历史数据：目标是全新初始化，不做旧表兼容、历史回填或双写。禁止业务对象落入 `public`。页面与业务规划见 [ops-platform-redesign.md](ops-platform-redesign.md)。

## 1. 原则与 PostgreSQL 适配

- 数据库仍用 PostgreSQL，独立 schema 命名为 `ipe_ops`；业务表、序列、索引、Flyway 历史表均在该 schema。JDBC `currentSchema=ipe_ops`、Hibernate `default_schema=ipe_ops`、Flyway `default-schema=ipe_ops` 和 `schemas=ipe_ops` 一致配置；部署角色预先创建并授权 schema。应用启动只迁移该 schema，不使用 `public` 作回退。连接后检查 `current_schema()` 和 `search_path`，禁止业务 SQL 显式访问 `public`；SQL 中必要时使用 `ipe_ops.table_name`。
- 参考 [阿里巴巴 Java 开发手册数据库规约](https://techforum-img.cn-hangzhou.oss-pub.aliyun-inc.com/%E9%98%BF%E9%87%8C%E5%B7%B4%E5%B7%B4Java%E5%BC%80%E5%8F%91%E6%89%8B%E5%86%8C%28%E7%BB%88%E6%9E%81%E7%89%88%29.pdf)：小写下划线命名、表字段有意义、主键 `id`、唯一索引 `uk_`、普通索引 `idx_`、禁止数据库外键和级联。手册的 MySQL 类型不是 PostgreSQL 原样语法：使用 `bigint generated by default as identity`、`boolean`、`numeric`、`timestamptz`、`jsonb`；布尔字段仍用 `is_` 前缀。
- 无 `FOREIGN KEY`/`REFERENCES`；逻辑关联保留 `xxx_id` 和明确索引。数据库仍负责主键、非空、唯一、检查约束；应用负责关联对象存在性、状态与生命周期，禁止依赖级联删除。
- 普通业务表使用 `id bigint`、`gmt_create timestamptz not null default now()`、`gmt_modified timestamptz not null default now()`；更新时间由应用显式维护，乐观锁 `version bigint not null default 0` 用于可编辑聚合根。追加日志可只保留 `gmt_create`。所有绝对时间统一存 UTC，查询按站点 IANA 时区转换，禁止使用无时区 timestamp 表示事件发生时刻。
- 金额 `numeric(18,4)`、电量 `numeric(20,6)`、瞬时电量采样按实际精度设计，Java 使用 `BigDecimal`；金额带 ISO 4217 币种。仅确有未知语义时允许 NULL，不用 0 假装数据可用。JSONB 用于结构多变的物模型、协议原文和快照，不用它替代主要查询字段。
- 有历史引用的业务主数据只停用或归档，不物理删除、不复用业务编码。无引用草稿删除需在事务中验证并锁住根记录。真实删除/清理仅限 demo 重置或受控保留策略，不用全表逻辑删除标志掩盖生命周期。

## 2. 逻辑关系

```text
station 1 ── N device N ── 1 product
                           └── N product_model_version
                         device ── N device_connector
                         device/connector ── N property_latest / property_sample
                         device/connector ── N charging_order ── N charging_bill
                                                └── N order_event
                         device/connector ── N energy_sample ──> energy_hourly
                         device/connector ── N alarm / command_record / protocol_message
protocol_code ── N protocol_document ── N protocol_document_section
station ── N tariff_plan ── N tariff_period; order 保存费率快照
```

线条仅代表应用层关系，不创建数据库外键。站点记录时区，设备和订单必须归属站点，历史订单保留站点、设备、枪口、产品与费率快照；设备移动站点不改历史。不存在组织/多租户/支付需求时不预建复杂平台域。

## 3. 表清单与字段字典

通用字段按上一节约定省略。`!` 表示非空，`?` 表示可空；未提及的状态以字符串保存，允许值由应用集中管理并在初始化 SQL 加 CHECK（需扩展枚举时通过迁移调整）。所有关系 ID 均为逻辑关联。

### 精简原则与建表范围

以下是完整候选模型，不要求首期一次性建齐。首期只实现产品与版本、站点、设备与枪口、运行状态、实时/历史属性、订单与账单、费率、告警、命令、协议文档及诊断必需的表；`energy_hourly` 是可重算的性能优化表，数据量小可先按事实数据查询，不预建。`device_event`、`order_event`、`protocol_message` 仅在对应事件时间线、协议诊断确有写入和查询需求时建立；不为假设的多租户、OSS/MinIO、支付或字典创建空表。实现前逐表确认写入方、使用页面及保留策略，没有明确用途的表不建。必要的唯一索引和数据完整性规则不能因为精简而省略。

### 协议文档

协议码沿用协议通道注册的稳定标识，例如 `YKC16`、`OCPP16J`；此处的协议码指协议类型代码，帧码或 OCPP Action 放在片段的 `frame_or_action`。本期一个文档绑定一个协议码，一个协议码可有多个不同版本或用途的文档。不增加协议字典表或文档关联表；产品的 `protocol_code` 和文档使用同一注册目录进行校验。未注册协议不可上传，已引用的协议码不得直接移除或改名。

| 表 | 主要字段 | 约束和典型索引 |
| --- | --- | --- |
| `protocol_document` | `protocol_code varchar(32)!`、`document_version varchar(64)!`、`title varchar(256)!`、`original_filename varchar(255)!`、`storage_key varchar(255)!`、`content_type varchar(128)!`、`file_size bigint!`、`sha256 char(64)!`、`status varchar(16)!`、`uploaded_by varchar(64)!` | `uk_protocol_document_storage_key(storage_key)`、`idx_protocol_document_lookup(protocol_code,document_version,status,id)`；status 为 ACTIVE/ARCHIVED；一个协议和版本可有多份不同用途的文件，不以协议码和版本强制唯一；名称和版本由用户填写，路径由服务生成 |
| `protocol_document_section` | `document_id bigint!`、`frame_or_action varchar(64)?`、`heading varchar(256)?`、`content text!`、`locator varchar(128)?`、`keywords varchar(512)?` | `idx_document_section_document(document_id,id)`、`idx_document_section_frame(document_id,frame_or_action)`；按协议和版本先查文档再查询片段；片段由人工维护或导入，本期不承诺自动解析 PDF |

两张表分别承载文件元数据和用于诊断的可检索片段；片段不是原文文件本身，保留当前位置 `locator`，可供现有诊断按协议码、版本、帧码/Action 或关键词检索。没有片段时文档仍可管理，诊断明确返回无匹配资料。无需支持片段的文档不产生片段记录。多文档命中时返回文档标题、版本和定位信息，不假设只存在一个文档。

文件本期存放在仓库根目录 `data/protocol-documents/`，通过配置项指定**绝对根目录**，启动脚本以项目根目录解析默认路径，避免工作目录变化导致文件丢失；该目录已被 `.gitignore` 忽略。现有工作区 `数据协议文档` 可以由用户通过上传导入，不能假设它就是运行时目录。数据库只保存服务端生成的相对 `storage_key` 和元信息，不保存本机绝对路径或文件二进制；原始文件名只供展示。使用随机不可预测的键及固定目录规则，禁止用户指定路径，规范化并校验解析后的目标在根目录内，拒绝路径穿越和符号链接逃逸。限制文件大小、扩展名和实际类型；下载由鉴权接口读取，不直接暴露文件目录。允许的类型和大小在配置中明确，上传失败展示原因。

上传时先写同目录临时文件，流式计算大小和 SHA-256，校验后原子移动到唯一目标，再保存数据库元数据；数据库提交失败时尽力清理目标文件，并提供孤儿文件/缺失文件巡检，不能把数据库事务误认为覆盖文件系统。更新文件生成新存储键且在成功保存后再清理旧文件；已建片段的文档替换时保留原版本并新建记录，避免定位信息失效。删除/归档操作在权限控制下执行：默认归档，文件和片段保留；允许彻底删除前检查诊断及引用，删除记录与片段在应用事务中处理，文件事务后删除，失败由巡检处理。数据库备份和文件目录备份需要一起做；缺文件或校验不符时明确报错。

后续可在应用层把存取封装为文件存储接口，再实现 OSS/MinIO；本期仅本地实现，不增加存储提供商表、配置表或远程存储依赖，也不承诺已完成迁移能力。

## 4. 无外键的一致性与并发

1. 创建/编辑设备在一个事务中锁定产品和模型版本（及站点），检查产品 PUBLISHED、版本属于产品且 PUBLISHED、站点可用、协议一致；产品发布/停用/删除也锁定同一产品行，再判断引用。统一锁顺序 station → product → model version → device → connector → order，减少死锁。数据库唯一索引兜底并发写。
2. 设备换绑只允许未激活、无订单及其他历史引用；锁设备并检查。站点迁移、新订单创建对设备使用相同锁；历史订单与计量记录使用发生时站点快照。删除与绑定必须在同事务遵守同一锁协议，单纯先查询再写不能防竞态。
3. 新建订单锁枪口并检查设备/枪口可用，活跃订单部分唯一索引兜底；状态转换使用 `where id=? and version=? and status in (...)`，并在同事务写 order_event。协议事务号作用域根据协议确定，不能假设跨设备全局唯一；每种协议以实际唯一域建立约束和幂等键。
4. 上报按稳定来源键去重，最新值通过带时间条件的 upsert 防止乱序覆盖；收到的原始账单先落库并判断幂等，再事务更新订单和事件。聚合来自事实表，可按时间范围重算并对账；不依赖单次内存事件。
5. 每日/按需执行巡检：设备指向的产品/版本/站点是否存在且匹配，枪口是否有设备，订单和账单关联是否有效，状态与活跃索引是否一致；发现问题记录并告警，不自动删除历史。

## 5. 初始化与项目改造

- 这是全新设计，旧库数据可以丢弃，但不要启动应用时自动清空已有库。实现时以新数据库或单独新建 schema 初始化；手工重置仅在明确选择的本地 demo 环境执行，并核实目标。
- 用全新 Flyway V1 建立上述表、注释、约束、索引和少量演示数据；将旧迁移移出新初始化路径，避免旧版本校验冲突。禁止用 `baseline-on-migrate` 掩盖未知 schema 状态；Flyway 历史表必须位于 `ipe_ops`。
- 配套改 JPA 映射、repository、SQL、事务和 API，再更新 simulator/protocol 的调用契约与前端；单改建表会使现有服务无法运行。不要在真实或共享数据库上自动 DROP schema，也不修改 `public` 的其他项目对象。
- 连接权限：应用角色具备 `ipe_ops` 的 USAGE 和必要表/序列权限；迁移角色拥有创建/更改权限，按环境分离。默认 `search_path` 只指向 `ipe_ops`（PostgreSQL 的 `pg_catalog` 系统解析除外），不设置 `public`。验证普通角色无 `public` 业务对象访问依赖；是否撤销 `public` 权限须由数据库管理员按实例范围评估，不能影响其他应用。
- 初始化检查：查询 `information_schema.table_constraints` 确认目标 schema 外键数量为零；检查 `flyway_schema_history`、序列和业务表位置；集成测试从空数据库启动，覆盖重复上报、并发绑定/创建订单、跨日统计及 schema 隔离。启动脚本和文档使用新的 JDBC schema 配置。
