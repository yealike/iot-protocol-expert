# 身份与授权

OPS 是统一身份来源。当前内置角色为 `PLATFORM_ADMIN`、`TENANT_OWNER`、`PROJECT_ADMIN`、`OPERATOR`、`ANALYST`、`VIEWER`、`QUOTA_ADMIN`、`AUDITOR`，支持作用域角色绑定、项目成员、服务账号与资源授权。业务端以权限点校验，不依赖页面隐藏按钮。所有角色、权限和站点授权的更新会增加账号授权版本，已登录会话在下一次请求失效。用户和角色更新写入运营审计日志。

Control 使用 OPS 的会话与稳定用户 ID，不缓存会话身份；Control 自身的 Agent、工具和环境策略仍与用户权限共同生效。Run 保存创建时的授权版本，排队执行、工具调用和事件流重新核验身份，授权发生变化后拒绝继续。Agent 工具查询运营数据时，OPS 使用服务身份获取真实用户并重新检查账号状态和用户站点范围，再与 Agent 策略范围取交集。

站点限制目前只对 Agent 工具业务查询实现细粒度控制。运营端尚未对设备、订单、汇总等所有查询实现站点行级过滤，因此站点受限账号的运营数据接口一律拒绝，不能将此限制当作运营端的完整多租户实现。后续要开放受限账号的运营页面，需先在列表、聚合、详情和写操作中统一实施服务端数据范围过滤并增加越权测试。

重构后的 OPS V1 基线包含授权版本字段，V2 将旧单角色数据迁移为当前内置角色。Control 关闭重复 Flyway，直接使用 `pep_platform` / `pep_agent`。历史会话及 Run 的归属按稳定用户 ID 读取；旧演示会话不会自动迁移，旧排队任务不能继续执行。请按 OPS、Control、Runtime 和前端的新启动顺序重启服务；运行账号需要对应 schema 的迁移权限。
